## 0.20.0-beta.342 — 2026-11-24

### Added

- **Vue pages can carry app state, Pinia included, across hydration** (`VueSetupAppContext`)
  A Vue page's `setupApp` hook runs on both sides, so a project could already install Pinia and have it work on each side separately. What it could not do is get the STATE across: Pinia fills its stores during the server render, the browser creates a fresh instance, and every store resets on mount — the visitor sees the server's values and then a flash as hydration replaces them with empty ones, and anything the client refetches is work the server already did. The `setupApp` context gains `transferState(key, () => value)` and `restoredState(key)`, so `ctx.transferState('pinia', () => pinia.state.value)` on the server and `pinia.state.value = ctx.restoredState('pinia')` on the client carry it over. A CHANNEL rather than Pinia support, because the framework does not depend on Pinia and should not, and the same two calls serve any store a project brings. The snapshot is a FUNCTION read after the render rather than a value read at registration, which is the part that would have been easy to get wrong invisibly: a store is empty when `setupApp` runs and full once the render has, so taking the value at registration would transfer an empty store every time while looking like it worked. Both members exist on both sides — `transferState` is a no-op in the browser and `restoredState` returns undefined on the server — so an isomorphic hook never has to branch on `isServer` for their sake. State that cannot be carried is dropped with an error naming the key rather than failing the page: by then the render has already succeeded, and turning a rendered page into a 500 over one unserializable value is the wrong trade. A test caught one real bug in that path: `JSON.stringify` RETURNS undefined for a function rather than throwing, so the first version emitted `{"key":undefined}` — not a syntax error, so the transfer would have silently carried nothing and still looked like it worked. A page that transfers nothing writes no script. Scope: pages. A Vue island has no `setupApp` hook, being a component rather than an app, and its server data goes through `useServerData`. See docs/VUE_APP_STATE.md.

## 0.20.0-beta.341 — 2026-11-24

### Fixed

- **A Vue island outside a Vue page loads its data on the server**
  `useServerData` reads its collector off Vue's SSR context, and only `src/vue/pageHandler.ts` ever created one. A Vue island rendered anywhere else — on a React page, a Svelte page, a static HTML page — therefore had no collector, and the hook does the correct thing in that case, which is to leave its state pending so the server markup matches what the browser starts with. The cost is paid at runtime: the island paints its loading state, then the browser fetches data the server already had in hand, a round trip after hydration. The island render path now creates a collector too, one per request and shared by every Vue island on the page, and passes it on Vue's SSR context so `renderToString` prefetches. Verified at each layer rather than assumed: a component rendered with a collector on the context produces `from server` instead of `pending`; the same component rendered through `renderIslandMarkup` inside a request does too, and outside a request still renders pending rather than throwing; and the payload reaches the document through the island page context. It goes to `window.__ABSOLUTE_SERVER_DATA__`, the SAME global a Vue page writes, because the browser build of the hook reads exactly one place — so the client needed no change at all, which is the part of this that could have gone wrong quietly. A page with no Vue islands, or none that load data, gains nothing: the collector is created on first use and the page context only asks, never creates.

## 0.20.0-beta.340 — 2026-11-24

### Added

- **Angular pages restore scroll position, and can preload lazy routes** (`AngularRouterConfig`, `BaseBuildConfig`)
  An Angular page that exports `routes` gets a router the build wires up, and that router had `withComponentInputBinding`, `withViewTransitions` and a navigation error handler but no scrolling configuration at all. Angular restores no scroll position and ignores a `#fragment` unless told to, so an in-page navigation landed wherever the previous view happened to be scrolled to. Measured in a browser on a routed page: scroll to 1500, navigate to another route, go back — the position was 0. It is now 1500, verified on the same page with the feature turned off and on. This mattered more here than in a plain Angular app, because the framework's own cross-framework navigation layer has always restored scroll: an Angular page was the one place inside an AbsoluteJS app where going back lost your place. `withInMemoryScrolling({ anchorScrolling: "enabled", scrollPositionRestoration: "enabled" })` is injected by default and `angular: { router: { scrollRestoration: false } }` turns it off, for an app that manages scrolling itself and would otherwise be fighting the router. Preloading is the other half and is deliberately NOT symmetric: `{ preloading: 'all' }` adds `withPreloading(PreloadAllModules)`, and it stays opt-in because preloading every lazy route spends bandwidth on code a visitor may never reach, which is a choice an app should make rather than inherit. The anchor-scrolling half is part of the same Angular feature flag and is enabled with it, but only the scroll restoration was verified in a browser.

## 0.20.0-beta.339 — 2026-11-24

### Added

- **A render that hangs is cut off and answers with its fallback** (`BaseBuildConfig`, `RenderingConfig`)
  A page render that never finished never answered. Measured on a real server with a React page whose Suspense boundary never resolves: the shell streamed and then nothing — the request did not complete, the document had no closing tag, and no error was reported. The only thing that ends that is Bun's HTTP `idleTimeout`, 240s here, which reaps the socket WITHOUT an error, so the visitor's request dies in silence four minutes later. `rendering: { timeout: 30000 }`, the new default, bounds it. The same page then answered in 1.6s with a complete document and the boundary's fallback in place, because React treats an abort properly: measured separately, aborting a render with a pending boundary finished the stream 16ms later, called `onError` once, and produced HTML containing both the shell and the fallback. So a cut-off render is a page showing its loading state rather than a connection that dies quietly. The default is generous deliberately: this framework is meant to host streaming and AI workloads where a render legitimately waits on a slow upstream — the same reasoning gave `idleTimeout` its 240s — and a boundary still pending after thirty seconds is a bug or a dead upstream far more often than a slow one. `false` keeps the old unbounded behaviour. Scope is stated rather than implied. It covers REACT's streaming render, where the abort reaches `renderToReadableStream`. It does NOT cover Svelte, whose renderer builds the whole document before the first byte and only chunks the result, so the `signal` it accepts stops the chunking of HTML that already exists rather than the render. And it does not touch streaming slots, which are already bounded at five seconds per slot: a first draft gave them the render budget as a default, and that change was DEAD CODE, because the slot policy fills `timeoutMs` in before anything reads it — caught by writing a test that asserted the behaviour and watching the slot resolve anyway. The timer is unref'd so a pending budget never keeps a process alive, which matters for `absolute export`; it is cleared when a stream finishes, since the budget covers the render and not the transfer; and `rendering` is in the production runtime allowlist, because a budget that worked in dev and silently did nothing in production would repeat the mistake `basePath`, `logging` and `shutdown` each made there. See docs/RENDER_TIMEOUT.md.

## 0.20.0-beta.338 — 2026-11-24

### Fixed

- **Two Svelte components streaming an await block no longer share one slot id**
  A streamed `{#await}` block got an id of `absolute-svelte-await-<index>`, and the index restarted at zero in every file — so two components that each streamed one block both produced `absolute-svelte-await-0`. A slot id is how a streamed chunk finds the placeholder it belongs to, and the symptom on a page rendering both was worse than a duplicate id. Measured in a browser on a page with two such components, before the fix: the FIRST component's hole showed the SECOND component's content, and the second component's own hole stayed on its pending markup forever, because only one resolution chunk was sent for the shared id. One component rendering another's data, and the other never resolving. The id now folds in a short hash of the component's path, so the same page renders `absolute-svelte-await-39aa85-0` and `absolute-svelte-await-d69c08-0`, each resolving with its own content — verified in the same browser, same page, immediately after. The path is hashed RELATIVE TO THE PROJECT ROOT with separators normalised: the value handed in is an absolute path on the build machine, so hashing it as given would make the same component produce a different id in a different checkout. Only the server and client halves of one build have to agree, so that would break nothing — it would just make a reproducible build impossible to verify, which is a strange thing to give up for no reason. It is deterministic rather than random for the reason that matters at runtime: the server writes the id into markup and the client matches it, and a random id would differ between the two and match nothing. A component lowered with no path gets a stable `anon` id that still cannot collide with a file that has one.

## 0.20.0-beta.337 — 2026-11-24

### Added

- **Islands can hydrate on interaction, or only while a media query matches** (`IslandHydrate`, `RuntimeIslandRenderProps`, `renderIslandResult`)
  An island could hydrate on `load`, `idle`, `visible`, or not at all. Two strategies are added and both exist for the same reason — not paying for a component nobody wants yet. `interaction` hydrates on the first pointer, touch, focus or key press on the island itself, for something heavy until someone reaches for it: a date picker, a rich editor, a map, where `visible` already pays the moment it scrolls past. `{ media: '(min-width: 48rem)' }` hydrates only while the query matches, and later if it starts matching, for a widget that belongs to one layout and not another, where `visible` pays for it even on the layout that hides it. The media listener is the difference between what this promises and "hydrate if the query matched at first paint": a window resized across a breakpoint or a phone rotated hydrates it then. `focusin` and not `focus`, because focus does not bubble and a keyboard user landing on a control INSIDE the island would otherwise never trigger it; `pointerdown` and not `click`, so the work starts on press; all of them passive, since none call preventDefault and a non-passive touchstart listener delays scrolling. A detached island stops listening rather than being held alive by its own media listener for the life of the document, which a test covers. A browser with no `matchMedia` hydrates immediately, the safe direction: an island that works beats one that never appears. The authored type takes `{ media: string }` so nobody can ask for `media` without saying which, while the markup carries one plain word in `data-hydrate` and the query beside it in `data-hydrate-media` — a media query has colons, parentheses and spaces in it, and none of that should have to survive being packed into an attribute every other strategy fills with a single word. That split lives in `core/islandHydrateMode.ts`, a module with no imports but its types, because TWO places build island markup: the shared helper for every server-rendered framework, and `Island.svelte`, which ships as source and compiles in the user's project so it cannot import the first — writing the media split into one and not the other would mean a Svelte island hydrating immediately where a React one waits for the query, which is exactly the quiet divergence a shared module prevents. Also fixed: an unrecognised strategy hydrated immediately and said NOTHING, so `hydrate="vislble"` behaved exactly like `load` and looked like the feature simply not working. It still hydrates — the safe direction again — and now warns in dev, naming the strategies it knows.

### Added

- **A dev toolbar that shows the islands and frameworks on the page**
  `docs/dev/absolute-studio.md` described a development dashboard in the PRESENT TENSE — a route at `/__absolute_studio`, an introspection API at `/__absolute_dev/*`, a state registry fed by `window.__ABS_STATE_REGISTRY__`, SSR metrics via `window.__MEASURE_HYDRATION__`, five panels — and none of its surface existed: not the route, not the API, not either global. Anyone following the document got a 404. What did exist was most of the DATA, under a different namespace: `/__absolute/routes`, `/__absolute/requests` and `/__absolute/vitals/summary` are real and already power `absolute routes` and `absolute inspect`. A toolbar now ships in the dev client instead, and it is a toolbar rather than a route for a structural reason: the valuable half of framework devtools needs THE PAGE. Which islands are on this page, of which frameworks, with which hydrate strategies and persist keys, is something a separate document cannot see — and it is the one view no other devtools can give, since React DevTools sees React and Vue DevTools sees Vue and neither can show a Svelte island inside a React page. Nothing new is instrumented for that panel: every island already carries `data-component`, `data-framework`, `data-hydrate` and `data-absolute-persist` in the markup the server and client both produce. The HMR panel reads `window.__ABS_HMR_APPLIES__`, the capped buffer the HMR client has kept all along and persists to sessionStorage — the first version of this shipped its own ring buffer before checking, which duplicated existing state and lost the persistence, so it was deleted. Verified against a running dev server in a real browser: the island table listing a Svelte and a Vue island with their hydrate strategies and persist keys, the network panel reporting 353 registered routes and the twelve most recent requests, and the HMR panel live-updating on a real file edit with the file, kind, outcome and 126ms. Three things the implementation is shaped by, each a real failure mode rather than a precaution: it mounts on `documentElement` because a soft navigation REPLACES document.body, so a toolbar inside it vanishes on the first navigation (verified by replacing the body and watching it survive); it renders in a shadow root, because a dev tool that restyles the app it is inspecting is worse than no dev tool; and installing is idempotent, because a soft navigation re-runs the page module entries and each install would otherwise add another keydown handler and another HMR subscription — the same accumulation that once made an island mount per visit SQUARED. One bug found by running it: the file column was empty for every HTML and CSS update, because the client read only `primarySource` while the server sends `sourceFile` for those — the server's own reader (dev/webSocket.ts) had always read both. An absolute path is shown as its last three segments with the whole path in the tooltip, since the raw value is seventy characters of the dev server's own disk layout before the part anyone reads. Deliberately NOT built, and the document now says so instead of implying otherwise: the element-to-component inspector and the state registry, both of which need per-framework instrumentation. Web only, dev only. See docs/dev/dev-toolbar.md.

## 0.20.0-beta.334 — 2026-11-24

### Added

- **analyze --modules and --treemap say which modules a bundle is made of**
  `absolute analyze` reported totals per CATEGORY — pages, hydration, client, islands, shared chunks, CSS — which answers "how big" and never "of what". A 400KB page bundle that should be 90KB is a question about one dependency, and `Pages 412 KB` cannot name it. `--modules` now breaks a build down by the modules inside it and `--treemap FILE` writes the same data as a self-contained SVG page. The first run on this repository's own example app found `@angular/compiler` at 462KB, 68% of everything shipped to a browser, which is exactly what a category total hides. Bun's bundler does not report what went into an output, so the bytes are attributed from the SOURCEMAP: every mapping segment names a source file and a generated column, so the bytes between one segment and the next belong to that source. Measured on the example server bundle, that accounts for 96.9% of 3.9MB across 1,325 sources, and the remainder is reported as unmapped rather than quietly dropped — a bundler's prelude and the glue between modules belong to no source file, and leaving them out would make every percentage add up to more than the bundle. Sourcemaps are required and off by default in production, so with none the command names the setting instead of printing an empty breakdown that would read as "your bundle contains nothing". It also looks in TWO places, because `sourcemaps: 'external'` deliberately moves the maps out of the served build into a private `sourcemaps/` directory keyed by each JS file's basename and strips the `sourceMappingURL` comment so source is not published: looking only beside the bundle found 1 of 96 maps here, the server one, and reported every client bundle as having none. Those private maps carry original source, so `/sourcemaps` is now in this repository's .gitignore, where it was missing. A dependency groups under its package and project source under its first two path segments, since a treemap of 1,325 files is a wall and a treemap of the 30 things that own them is a report; a nested dependency groups under the package that actually ships it. The treemap page carries no script, no CDN and no network reference, because it has to open from a file:// path in a browser with nothing else available. Area is proportional to bytes, verified in a browser on the real report, where the median error across 46 groups was 0.03 of a percentage point. Two mistakes worth recording, both caught by a test rather than by reading: the attribution charged a newline byte to the LAST line of a file, which has none, so the attributed bytes exceeded the file by one; and the private-sourcemap location was missed entirely at first, which made the whole report server-only. The enforceable half of this item already existed and is unchanged — `analyze --check` against `sizeBudgets`, and `ls --budget` — so this adds the explanation, not the gate. See docs/BUNDLE_TREEMAP.md.

## 0.20.0-beta.333 — 2026-11-24

### Fixed

- **A declared env schema validates its formats, and the CLI can read it** (`defineEnv`)
  `defineEnv` was already exported and already did the hard part — a TypeBox schema per variable, coercion from the strings the environment actually holds, defaults, a readable failure table and a secret-looking name reported as `set` rather than printed. It had NO caller, no test and no mention anywhere in the repo or its docs, and two things were wrong with it in practice. First, a string format could never pass: TypeBox ships no format validators, `FormatRegistry` starts empty, and a schema naming a format it does not hold fails CLOSED — so the obvious way to declare a database URL, `Type.String({ format: 'uri' })`, rejected every value including correct ones with `Unknown format 'uri', got "postgres://user:pw@localhost:5432/db"`, a message that blames the value. An app written that way could not start at all. Ten formats are registered now (date-time, duration, email, hostname, ipv4, ipv6, uri, uri-reference, url, uuid), deliberately as simple checks rather than full grammars: a format here answers whether someone pasted the wrong KIND of thing into a variable, and anything needing a precise grammar should carry a `pattern`, which TypeBox has always enforced itself. Second, `absolute env` could not see a schema: it knew one thing, a regex for `getEnv('X')`, so a project declaring its environment the typed way got `No getEnv() usage found under src/.` — the command said nothing at all precisely for the projects doing it the recommended way. It now reports both sources, labelled, because they answer different questions: the schema says what the project DECLARES, with a type, a default and whether it is optional, and the scan says where a variable is READ, so a key in the scan and not the schema is usually one that should be declared. `--check` fails on a variable set to the WRONG thing (`✗ PORT number invalid "notanumber"`) and not only on an absent one, which is the half worth running in CI. Reading the schema needs a mechanism, because `defineEnv` validates at import and throws on the first missing variable — the very thing the command is there to report — so the CLI sets `ABSOLUTE_ENV_INSPECT` around the import and `defineEnv` records its properties and returns a schema-shaped placeholder instead of validating; the alternative was asking a project to export its schema separately from the call that consumes it, two things nobody would keep in step. Three mistakes caught by running it rather than reasoning about it: the placeholders were first built with TypeBox's `Value.Create`, which refuses a formatted string with no default and so failed on exactly the `format: 'uri'` case the registry exists for; `uri` first accepted relative references by falling back to parsing against a base, which made the format validate NOTHING, since every string is a legal relative path, `"not a uri at all"` included; and the inspection registry accumulated across reads, so a second module was handed the first module's variables. See docs/TYPED_ENV.md.

## 0.20.0-beta.331 — 2026-11-23

### Added

- **Third-party scripts have a component, a strategy, and run once** (`Head`, `Metadata`, `ScriptProps`, `ScriptStrategy`, `generateHeadElement`, `insertedScriptAttributes`, `scriptAttributes`, `scriptIdentity`, `scriptTag`)
  There was no supported way to add a third-party tag: no framework had a `<Script>` component, and `generateHeadElement` rendered meta tags, preload links, speculation rules and JSON-LD but had no option for a script, so a project wrote the tag into its own markup. That is also how it ended up running more than once. Measured in a browser before any of this existed, on two pages that both carried one tag with its own counter: a soft navigation read 1, then 2, then 3 going back, because the navigation layer recreates every executable script of the page it swaps in. A real analytics tag double-counts every pageview after the first and a chat widget re-initialises. Now `<Script src="…" />` (React) or `scripts: [{ src: … }]` on any page head renders the tag with a strategy — `beforeInteractive` undeferred, `afterInteractive` deferred (the default, since a third-party tag that blocks parsing is the thing this avoids), or `lazyOnload`, added by the client after the window loads on an idle callback. Each tag carries an identity, `id` or `src`, and deduplication is keyed on THAT and deliberately not on `src` for every script: a page's own hydration index has the same `src` on both sides of a navigation and must run again, which is the mechanism by which the incoming page mounts at all. When the live document is already running a script with that identity the ELEMENT IS MOVED into the new page rather than recreated, because the browser keeps an "already started" flag on the element itself, so a fresh node with identical attributes would fetch and execute again. Verified on a live server across four cases: both pages carrying the tag (1 after the navigation, was 2), two navigations (1, was 3), `lazyOnload` (1), and the asymmetric case where the second page does not carry the script at all and the visitor returns (1). The page's own React app still hydrates on arrival in each. Angular gets no component form and that is not an omission: its template compiler drops a `<script>` element silently — `preparseElement` returns null for one, with no error — so a component could render the tag and nothing would appear. A head rendered as a string has no component to run an effect later, so `lazyOnload` there renders a small inline bootstrap that checks the document for the tag first; both it and inline source neutralise a literal `</script`, which would otherwise close the element early and spill the rest of the page as markup, and which is not hypothetical in code pasted out of a tag manager. On a Svelte page the request nonce is applied server-side after rendering, because a component compiled in the project cannot read it and the tag would otherwise be rendered and then refused by the page's own policy. Not to be confused with `registerClientScript`, which serializes a function of yours to run after Angular hydration. See docs/THIRD_PARTY_SCRIPTS.md.

## 0.20.0-beta.328 — 2026-11-23

### Fixed

- **placeholder="blur" generates a placeholder instead of doing nothing**
  `types/image.ts` said `blurDataURL` was "auto-generated for build-time images" and nothing generated it: `generateBlurDataURL` existed with no caller anywhere in the repo, so `placeholder="blur"` resolved to `undefined` and the prop was accepted and silently did nothing unless the project computed a base64 thumbnail itself. All four framework Image components already consumed `generateBlurSvg`; only the thing that produces the data was missing. The build now generates one for every png, jpg, jpeg, webp and avif under the assets and public directories — measured at 3.2ms and 255 bytes each, so a hundred images cost about a third of a second — and writes them beside the build as a server-only file. SVG is excluded deliberately, being already tiny and resolution-independent, as are sources over 12MB, where decoding to produce an 8x8 thumbnail costs more than the placeholder is worth. The delivery is where the real cost is, and each page carries only the placeholders for the images IT renders. The browser asset manifest that already rides every page ships the whole app's entries; doing that with blur data would put 255 bytes times every image in the project into every page — 25KB a page at a hundred images, and base64 webp barely compresses — for images most pages never show. The filter is a pure function of the rendered HTML, so there is no per-request collection and nothing for two concurrent renders to interleave. The client gets them because the same component renders on the server and then hydrates: were the lookup server-only, hydration would recompute the style without a placeholder and strip the blur the server had just painted. Soft navigation works for the same reason, since the next page's HTML carries its own. An image the build never saw — a remote URL, one chosen at runtime — still takes an explicit `blurDataURL`, and the type comment says so now instead of promising something automatic. See docs/IMAGE_BLUR_PLACEHOLDERS.md.

## 0.20.0-beta.327 — 2026-11-23

### Added

- **Svelte accessibility warnings are reported instead of discarded**
  `absolute typecheck` already ran svelte-check, which detects accessibility problems — an `<img>` with no `alt`, a `<div>` with a click handler and no keyboard handler, a static element with a click handler and no ARIA role — and every one of them was discarded. Svelte reports them as WARNINGS, so `--threshold error` kept them out of the output and `parseSvelteCheckOutput` dropped any that got through. Probed with a Svelte page containing three textbook violations: typecheck passed clean and said nothing. They are now reported. They do NOT fail the typecheck, and that is deliberate — a warning that fails a build is an error by another name, and a project adopting this version would go from green to red on code it had not changed. Only accessibility warnings are surfaced, not every Svelte warning: measured on this repo, there are 16 non-accessibility warnings, all in the framework's own components and none actionable by a project using it, against 0 accessibility warnings, so showing everything would be noise that buries the type errors above it. Long lists are capped at 20 with a count, for the same reason. Two things had to be fixed to make the report readable, both found by looking at the output rather than reasoning about it: svelte-check exits 0 even with warnings present, so the `exitCode === 0` early return skipped the report entirely; and it hands back paths already relativised against something else and lowercased on a case-insensitive filesystem, so `relative()` returned a climb out of the project (`../../../../../users/you/project/src/…`) instead of `src/…`. The path fix applies to svelte-check's errors too, which had the same defect. Not covered: React, Vue and Angular have no equivalent checker already running, and `eslint-plugin-absolute` is a separate package, so rules there are not in reach of this repo.

## 0.20.0-beta.326 — 2026-11-23

### Fixed

- **Soft navigation moves focus into the new page and announces it once**
  A full page load moves focus to the new document and a screen reader reads it; a soft navigation replaces the page with neither, so unless something does it deliberately a keyboard user is left focused on a link that no longer exists and a screen reader user is told nothing happened. Focus now moves into the new content — the page's own `autofocus` first, then its heading, then the main landmark — and the heading is preferred over the landmark because it does both jobs at once: it moves focus past the navigation a keyboard user would otherwise tab through again, and it names the page just arrived at. A heading is not focusable, so it is given `tabindex="-1"`, which keeps it out of the tab sequence rather than adding a stop to every page, and the attribute is removed once focus leaves so an app's own `[tabindex]` styling and queries still see the page it wrote; a heading that already had one keeps it. Focus is set with `preventScroll`, because `reapplyScroll` runs afterwards and decides where the page sits, including restoring a saved position on a traversal — without it the browser would scroll the heading into view first and the page would visibly jump. The announcer's conflicting roles are the other half: the live region carried `role="status"`, whose implicit politeness is POLITE, together with an explicit `aria-live="assertive"`, so it declared itself both and each screen reader picked a winner. The explicit attribute is the one that says what was meant, so the role goes rather than the attribute — `role="alert"` would agree with assertive but also claim the message is important and time-sensitive, which a page title is not. Announcing is now conditional on focus NOT having moved: focusing the heading already makes a screen reader read it, so announcing as well says the same thing twice, and the live region is the fallback for a page with nothing to focus rather than a second channel. One implementation defect was caught by its own test: the targets were written as a single selector list, and `querySelector` returns the first match in DOCUMENT order rather than the first selector that matches, so `main h1, main` handed back the `<main>` enclosing the heading and focus landed on the whole content region instead of its title. They are tried one at a time now.

## 0.20.0-beta.325 — 2026-11-23

### Added

- **Run several server processes sharing one port** (`BaseBuildConfig`, `ClusterConfig`, `ClusterPlan`)

Measured on oven/bun:1.4.4 with a CPU-bound handler, four workers took 3,245 req/s to 11,077 — a 3.4x gain, split almost perfectly at 10891/11236/11253/11107. ## 0.20.0-beta.324 — 2026-11-23

### Added

- **Production servers drain in-flight requests before exiting** (`BaseBuildConfig`, `ShutdownConfig`)
  Measured first, because the plan item describes a feature and what was underneath it is a defect: a request 300ms into 1500ms of work, interrupted by SIGTERM, reaches the client as ECONNREFUSED — not a 502, not a truncated body, the connection is gone. That happened on every deploy, scale-down and rollout, for every request in flight. A production server now finishes them first, then exits 143, the conventional code for a signalled process, so nothing downstream reads a clean shutdown as a crash. Readiness reports `shutting-down` from the moment the signal arrives, separately from and before the registered checks, because no amount of healthy dependencies changes the fact that the process is leaving; liveness deliberately stays `ok`, since a failing liveness probe gets the process KILLED, which is the opposite of draining it. `readinessGraceMs` exists because the first version of this did not have it and needed it: refusing new connections is the first thing a drain does, so a probe arriving just after the flip got a connection error rather than the clean 503 — measured as `connection refused`, with the flip in place and working, which made it unobservable over HTTP and left a balancer learning from failed connections. With an 800ms window the same probe reads `unready`. It defaults to 0 because the right value is the balancer's own deregistration interval, which the framework cannot know, and because a default wait would slow every Ctrl+C for a benefit only an orchestrated deployment sees; SIGINT ignores it outright, being an operator at a terminal rather than a rollout. Taking a signal at all is the exception this earns — `flushAccessLogOnExit` still refuses to, and for the reason stated there: a listener suppresses the default terminate, so whoever installs one must exit the process. So the deadline is armed before the drain is awaited and unref'd so it can never hold the process open, a stop that throws still exits, and a second signal exits at once rather than making someone reach for SIGKILL. Production only — dev servers restart constantly under HMR and the dev CLI already owns that lifecycle. `shutdown: false` opts out. See docs/GRACEFUL_SHUTDOWN.md.

## 0.20.0-beta.323 — 2026-11-23

### Added

- **Angular AOT output is cached between production builds**
  Angular AOT was the largest cost in a production build that nothing cached: `aot/perform-compilation` is ~744ms of a ~2.3s build on the example app, while the Angular linker and resource caches (which already persist across production builds, contrary to plan item 5.19's note that caches are dev-only) only cover the vendor passes. A hit now takes `aot/compile-files` from ~977ms to ~200ms and skips `perform-compilation` entirely. The compile is one program over every entry point, not file by file, so the unit is the whole emit — all of it or none. What makes it safe to key is that the program reads 609 files on this app, 603 of them in `node_modules`, and hashing every one costs 16ms against the 744ms saved: a 46x margin, so the cache validates against the complete set the compiler actually read rather than a guessed subset. The file list cannot be known before compiling, so it is recorded during a compile and re-checked next time, which is sound because any file newly pulled into the program must be imported by one already in it, whose content therefore changed. The subtlety a naive version gets wrong is that the compiler never reads project sources from disk — it is handed copies with `templateUrl` and `styleUrls` already inlined — so a key built from disk contents would not move when a template changed and the cache would serve a component compiled against the old HTML; hashing the effective content the compiler is handed folds template and style changes in automatically. Verified by changing an external template, a component `.ts`, a non-entry project file and a `node_modules` declaration, and confirming each forces a recompile; cached output was also checked byte-identical to an uncached build. Compiler options, the TypeScript lib directory, the style-preprocessor config and the lockfile are in the key. Everything fails open — a corrupt entry, a truncated write, a missing file or an unknown format version is a miss and a normal compile, never a build failure — and entries are renamed into place so a build that dies midway leaves nothing half-written. `ABSOLUTE_AOT_CACHE=0` disables it. A fresh checkout has no cache and is unchanged; this is for repeat builds and for CI that restores `.absolutejs/cache`. See docs/BUILD_CACHE.md.

### Changed

- **The app error-hook check is pinned to Elysia’s declared types instead of guessed structure**
  The static error page is a fallback: it renders error.html for a thrown page route only when the app has no error handling of its own, which `src/core/appErrorHooks.ts` worked out by walking Elysia's `~hookChain` as an untyped structure. ## 0.20.0-beta.318 — 2026-11-23

### Added

- **Rate limiting, counted by connection address with a bounded store** (`BaseBuildConfig`, `RateLimitConfig`, `RateLimitRule`)
  `rateLimit: { limit, rules }` refuses with `429`, `Retry-After` and the IETF `RateLimit-*` headers from `onRequest`, so a refused request never reaches a handler — not doing the work being the point. Nothing was rate limited before, anywhere. What is limited is deliberate: app routes only when `limit` or a rule says so, since a framework that starts refusing a project's traffic at a number it picked is worse than one that does nothing; the vitals endpoint by default at 60 a minute per client, because it is an unauthenticated POST sink the framework mounts on the app's behalf and a real page sends one batch per load; and the health endpoints never by a global limit, because a 429 to a readiness probe is a failed probe and a failed readiness probe takes the process out of rotation — a limit there turns a burst of probes into the outage it was meant to prevent. A test caught the first version doing exactly that, since a global limit covers every path no rule names. A rule naming a health path still applies: a project that means to limit its own probes may. Requests are counted by connection address (`server.requestIP`), not `x-forwarded-for`: a client that chooses its own key has no limit, so a fresh header value per request would be a fresh allowance per request. `trustProxy: true` opts in and belongs only behind a proxy that sets it — the opposite default from `isHttpsRequest`, which may read its header freely because spoofing that can only turn `Secure` on, whereas spoofing this would turn enforcement off. The bucket store is capped (`maxKeys`, default 10000) and evicts the least recently seen, because an attacker picks the keys and an unbounded map would make the limiter the memory-exhaustion vector it exists to prevent; eviction is by last request rather than first insert, so a client still sending traffic keeps its bucket instead of earning a fresh allowance. Counting is per process: two instances behind a load balancer each allow the configured rate, which is what clustering (plan item 5.9) has to settle. See `docs/RATE_LIMITING.md`.

### Fixed

- **A readiness probe no longer costs a check run per request** (`HealthConfig`)
  The readiness endpoint added in beta.315 ran every app-registered check on every request, and it is an unauthenticated GET — so it was an amplifier pointed at whatever the app registered. Measured with a check doing one 2ms database query: 500 concurrent probes produced 500 invocations in 37ms. A report is now reused for `cacheMs` (default 1000) and concurrent probes share one run rather than each starting their own; the TTL alone would not have helped, since requests arriving together all miss a cache nothing has filled yet. The same 500 probes now cost one invocation. An orchestrator probing every 2-5s never sees a cached answer, which is the point — this collapses floods, not probes — and `cacheMs: 0` restores a run per probe. Registering or removing a check invalidates a cached report, because a report describes the set of checks it ran: otherwise a process that answers a probe before registering its database check would report `ok` for a second on the strength of having had no checks. Rate limiting is deliberately not the tool here, since refusing a readiness probe takes the process out of rotation.

## 0.20.0-beta.316 — 2026-11-23

### Added

- **An error-reporter hook for server-side render errors** (`ServerErrorKind`, `ServerErrorReport`, `ServerErrorReporter`, `onServerError`)
  `onServerError((report) => …)` is notified of every server-side error the framework catches: each framework's page render, React's and Vue's streaming paths, static and HTMX pages, a failed partial-prerender hole, and a file route's `load`. Before this they went to `console.error` and nowhere else, which on a server is a line in a log nobody reads — the error was known to the process and to no one. The intended sink is `@absolutejs/errors`, the ecosystem's exception capture, whose `captureException` suits a reporter exactly since capturing an error can never itself fail; a reporter is a plain function, so anywhere else works too. An Elysia-level error hook is not an alternative: each page handler catches its own render failure in order to serve the error convention and returns a 500, so the error never propagates as an Elysia error and `onError` never fires — these nine sites are the inside of those catches. The report carries the error, which framework, the page, the method and path, and the request's correlation id, so a captured issue lines up with the access log line for the same request and with the id a visitor can quote from the response header. The query string is deliberately left out: it can carry a session token or an email, and the path says which route failed. `kind` distinguishes failures that are not interchangeable — `page` threw before anything was sent and the visitor got an error page; `stream` threw after the first byte, so the visitor has a partial page and no status code can say so; `hole` is a partial-prerender slot whose fallback stands, a degradation rather than a failure; `load` is a file route's loader. `console.error` still happens, because a framework that goes quiet once a reporter is registered has traded one blind spot for another. A reporter runs inside the `catch` already handling a failed render, so it is isolated three ways: a throw is caught and the remaining reporters still run, so the visitor still gets the error page; a returned promise is not awaited, only its rejection caught, so an error page never waits on a round trip; and a reporter's own failure goes to the terminal rather than back through the reporters, which is how a reporter that always throws would otherwise write a stack overflow. Also fixed on the way: `logging.requestIdHeader` was read only by the access log, so with a configured header an error report during the request would have minted an id under the default name and the log line after it would have reused that minted id — adopting the proxy's id in neither. The configured name now has one home that every caller reads. Browser errors and source-map symbolication are not a gap here to fill later: they belong to `@absolutejs/beacon` and `@absolutejs/errors`'s ingest, which have them. See `docs/ERROR_REPORTING.md`.

## 0.20.0-beta.308 — 2026-11-22

### Security

- **CSRF and form-action cookies are `Secure` behind a TLS-terminating proxy**
  The CSRF token cookie and the form-action flash cookie decided their `Secure` flag from the request's OWN protocol — `new URL(request.url).protocol === 'https:'`. A proxy that terminates TLS forwards plain HTTP, so on most real deployments that is `http:` and the flag was omitted. A browser then sends those cookies over plain HTTP to the same host, where anyone on the network can read them, and a readable CSRF token defeats the token half of the check it exists for. The codebase already disagreed with itself about this: `secureHeaders()` consulted `x-forwarded-proto` and the cookie code did not, so measured across deployment shapes they differed on exactly the two that matter — behind a TLS-terminating proxy, and behind a CDN in front of a load balancer. Both now use one `isHttpsRequest`, which reads the connection, then the first value of `x-forwarded-proto` (the client's own hop; later values are the proxies in between), then RFC 7239 `Forwarded: proto=`. Trusting a client-supplied header is safe in this direction and only this one: it is OR-ed with the real protocol, so it can only ever turn `Secure` ON. A client that lies marks its own cookies `Secure`, which leaks nothing — at worst its browser declines to send them over http — so this needs no trust-boundary configuration to be correct. A genuinely plain-HTTP deployment still gets no `Secure` flag, which is pinned by a test, because a cookie the browser refuses to send back would break the check instead of hardening it.

## 0.20.0-beta.307 — 2026-11-22

### Added

- **server-rendered and static HTML responses are compressed**
  Build-time precompression writes `.br` and `.gz` beside every compressible file, which covers static assets and cannot cover a page handler's response: that HTML is produced per request, and even a static HTML page served through `handleHTMLPageRequest` is read and returned by the handler rather than by the asset plugin, so the `.br` already on disk beside it was never reached. Measured against the example app in production, asking for `br, gzip`: every page came back with no `content-encoding`, and compressing those exact bodies saved 64-77% — react 2670 to 933 bytes, angular 4045 to 1474, htmx 6013 to 1366. Non-streaming HTML responses are now compressed where the client accepts it, in the one place that already buffered the body to hash an ETag, so it costs a compress call rather than another buffering pass. Two details that are wrong if left out: the response carries `vary: accept-encoding`, without which a shared cache can hand brotli bytes to a gzip-only client, and the encoded body gets its own ETag, without which the conditional-request path can match a client holding the identity version and answer it with brotli. The encoding is therefore settled before the ETag, which also means a 304 skips the compression work. Fixing the compressor was not enough on its own: the static HTML and HTMX handlers called the wrapper without a request, so there was no `accept-encoding` to read and nothing compressed however correct the compressor was. STREAMING pages are deliberately left uncompressed — compressing through this path buffers the body and forfeits the fast first byte that is the point of streaming, so covering them needs a streaming compressor and is still open.

## 0.20.0-beta.306 — 2026-11-22

### Fixed

- **the Angular SSR dev-log filter no longer leaks a console.log wrapper per render**
  Angular logs "Angular is running in development mode." on every `bootstrapApplication`, which on a server is once per request, so the SSR renderer filtered it by saving `console.log`, replacing it, and restoring it in a `finally` — around each render. Under concurrency that leaks: each render captures whatever is installed when IT starts and reinstalls that when IT finishes, so the last render to finish wins and a wrapper is left behind. One accumulates per round of concurrent renders, and every `console.log` anywhere in the process then walks the whole chain. Measured with eight concurrent renders completing in start order: after 60 rounds — 480 renders, a few seconds of traffic — 20,000 `console.log` calls went from 0.3ms to 79.7ms, a 240x degradation that keeps climbing, and a message containing the filtered phrase was swallowed for the life of the process. The accumulation does not depend on anything logging during a render; the install and restore were unconditional, so a production server rendering Angular pages concurrently made all of its own logging progressively slower. The filter is now installed once, with a counter marking whether a render is in flight: nothing nests, nothing accumulates, and it is only active while rendering rather than forever. It is also narrowed to Angular's own wording, so an application line that merely shares the phrase is no longer hidden. This does not change render throughput — measured at 4,138 req/s against 3,960-4,401 before, which is the same noise band. Angular SSR costs a full application bootstrap per request and that is where its time goes.

### Added

- **`absolute bench`, with a committed baseline and a regression gate** (`BaseBuildConfig`)

### Added

- **Angular pages replay clicks made before they hydrate**
  A click made before an Angular page finishes hydrating now arrives once it has. ## 0.20.0-beta.261 — 2026-11-21

### Fixed

- **A Svelte page that streams an `{#await}` block hydrates instead of going inert**
  A Svelte page that streams an `{#await}` block now hydrates like any other. ## 0.20.0-beta.260 — 2026-11-21

### Fixed

- **An `error` convention no longer turns off streaming for React pages**
  Adding an `error` convention turned streaming off for React pages. The handler buffered the whole document whenever an error convention existed for the page or anywhere in the app, so a page that streamed its shell in milliseconds began arriving only once its slowest Suspense boundary had resolved — measured at 603ms to first byte against 11ms for the same page without the convention. Nothing announced it: adding `error.tsx` looks unrelated to streaming, and the only symptom is a page that got slower. The buffering existed so the handler could answer a failed render with the convention's error page instead of half a document, and it was not needed for that: the only error that can be answered with an error page is one in the shell, and `renderToReadableStream` rejects for those before a byte is written, so the handler's catch still gets it. React pages now stream whether or not an error convention exists, and a shell error still answers with the convention's page.

## 0.20.0-beta.214 — 2026-11-20

### Security

- **The no-JavaScript form result cookie is signed** (`getActionState`)

The absolute_csrf cookie holds a random value and the hidden _csrf field, or the x-absolute-csrf header, holds an HMAC of it, so a cross-site page cannot produce a matching pair even though the browser attaches the cookie for it. getCsrfToken() mints the token while rendering the way getCspNonce() does, the runtime sets the cookie and marks the page private, no-store, and the token is stripped from the body before validation. The next reload renders the edit on the server too, so the hydration-mismatch overlay no longer appears. Before, a React island edit left the browser on the old island bundle (every reload then failed hydration), and a Svelte or Vue island edit changed nothing at all. Editing the React page that hosts the islands, or a component it imports, also updates in place again; before, the update could leave lifeless copies of the islands on screen. This covers islands rendered by React and HTML pages, and the island registry may live outside your framework directories (for example `src/islands/`). Angular islands, and edits to the registry file itself, still reload the page.
- **Errors thrown by routes are logged for API and fetch requests too, not only page requests**
  When your app has no `onError` of its own, a route that throws was only logged for page and HTMX requests, and only when the project had an HTML or HTMX `error.html`. The same route called with `fetch` or `curl` (`Accept: */*`) or asking for JSON returned Elysia's generic 500 and wrote nothing to the log, in development and production, so a mistyped `asset()` key in an API route failed silently. Every unhandled route error is now logged once on the server, with the method, path and stack, whatever the request accepts. Responses are unchanged: the error details stay out of the response body, 404s and thrown `status(...)` responses are not logged, and an app that registers its own `onError` still handles (and logs) errors itself.
- **React Server Components pages named `*RSC.tsx` no longer get a doubled `RSCRSC` manifest key** (`asset`, `BaseBuildConfig`)
  A React Server Components page whose file name already ends in RSC got the suffix twice: `pages/HomeRSC.tsx` was `asset(manifest, 'HomeRSCRSC')`, so the natural `'HomeRSC'` was missing from the manifest and the route failed only at request time. Such a page is now `asset(manifest, 'HomeRSC')`. The doubled key still works as a deprecated alias for the same bundle and prints a one-time warning in dev naming the new key. If `pages/Home.tsx` and `pages/HomeRSC.tsx` both exist, `Home.tsx` keeps `HomeRSC` (its key is unchanged), `HomeRSC.tsx` stays at `HomeRSCRSC`, and the build warns about the clash.
- **`@absolutejs/absolute/react/components` can be imported from React Server Components** (`SuspenseSlot`, `StreamSlot`, `Link`)
  Importing anything from `@absolutejs/absolute/react/components` (for example `SuspenseSlot`) in a React Server Component crashed the page with `TypeError: createContext is not a function`, because the entry also defines `Link`'s context and React's server build has no `createContext`. A server component that imports the entry now gets a server components version of it: `SuspenseSlot`, `StreamSlot`, `Head`, `Image` and `JsonLd` render on the server as before, and `Link` and `usePrefetch` come from a "use client" module, so a server component can render `<Link>` and it hydrates as a client component. Wrapping these in your own 'use client' file is no longer needed. As with any client component, `<Link>` props passed from a server component must be serializable (no event handlers).
- **HTML and HTMX error and not-found pages load their stylesheets in production**
  The HTML and HTMX `error.html`, `not-found.html` and `loading.html` pages were copied into the build as written, so a stylesheet or script linked relative to the source (such as `../../styles/indexes/site.css`) returned 404 and the error page showed unstyled. These pages now get the same hashed asset URLs (and font tags) as your other HTML and HTMX pages.
- **Svelte component style edits now apply in dev without a reload**
  Editing only the `<style>` block of a Svelte component in dev hot-updated the component, but the page kept the old styles until a full reload: the browser reused the component's previously loaded stylesheet module. Each version of a component's styles now gets its own URL, so style edits apply immediately.

A sibling `blog/[slug].server.ts` can export `load`, whose result becomes the page's props, and `beforeHandle`, which can answer the request first (for example with a redirect). The route module checks types: `load` must take the route's params and return the page's props, so a renamed param or a missing prop is a type error. Explicit routes stay the default and win over a file route for the same path. In `absolute dev`, adding, renaming or removing a route file updates the routes without a restart. Catch-all, optional and group segments, Vue, Angular and HTML routes, and per-folder conventions are planned. See docs/FILE_ROUTER_PLAN.md.
- **Form actions: one handler for forms that work without JavaScript and update in place with it, on React, static HTML and HTMX pages**
  `defineAction(path, { body, handler })` defines a form action: a POST route that checks the form against an Elysia `t.Object` schema and works with or without JavaScript. Without JavaScript a plain `<form method="post">` posts, the browser is sent back to the page (or to `redirect`) and the page shows the result: React and other SSR pages read it with `getActionState(action)` and pass it as a prop, and static HTML and HTMX pages get the errors, the success message and what the user typed written into `<form data-absolute-action>` by the server. With JavaScript, React's `useFormAction` hook (from `@absolutejs/absolute/react/hooks`) and `enhanceForms()` for plain pages (from `@absolutejs/absolute/client`) submit without a reload and expose pending, the typed result and one error message per field. HTMX `hx-post` forms get the action's `htmx` fragment, or behave like a plain post. Cross-site posts are refused (403), bodies over `maxBodySize` (default 10 MiB) are refused before they are read (413), and JSON clients such as Eden get JSON.
- **Layouts and partials for HTML and HTMX pages with `<abs-include>` and `<abs-slot>`**
  HTML and HTMX pages can share markup with `<abs-include src="../partials/header.html"></abs-include>`, which is replaced at build time with the file's contents. Paths are relative to the including file, and included files can include others. A layout marks where content goes with `<abs-slot>` and `<abs-slot name="head">`; a page fills the slots through the include's children and `<template slot="head">`. Includes are expanded before asset paths, image optimization and island rendering, so included markup gets all three. A missing file or an include cycle fails the build and shows the chain. Only the `.html` files directly in `pages/` are pages. In dev, editing a partial or layout updates every page that includes it. See docs/HTML_INCLUDES.md.
- **Internationalization: locale routing, typed ICU message catalogs, React and Svelte translation APIs, hreflang links and a per-locale sitemap** (`defineI18n`, `i18nPlugin`, `getRequestLocale`, `I18nProvider`, `useI18n`, `setI18n`, `getI18n`, `createTranslator`, `defineMessages`, `formatMessage`, `Metadata`, `generateHeadElement`, `Head`, `SitemapConfig`, `BaseBuildConfig`)
  Apps can now be translated. `defineI18n()` takes your locales, the default locale's messages and a loader for each other locale, and `i18nPlugin()` works out each request's locale from the URL prefix (`/fr/about`), the domain, or the visitor's cookie and `Accept-Language` header. Handlers get `locale` and an `i18n` object: `i18n.t('key', params)` formats ICU messages (plurals, select, numbers, dates) with the platform's `Intl`, and `i18n.payload(['namespace'])` returns the messages a page needs to hydrate, which you pass as a page prop. React pages read them with `I18nProvider` and `useI18n()` from `@absolutejs/absolute/react/hooks`; Svelte pages with `setI18n()` and `getI18n()` from `@absolutejs/absolute/svelte`. Message keys and their parameters are type-checked against the default catalog, and a locale missing a key is a type error. `i18n.alternates()` builds hreflang links, which the `alternates` field of `Metadata` renders in `generateHeadElement` and the React and Svelte `Head` components. Setting `sitemap.i18n` lists every page once per locale with hreflang alternates. Svelte pages get the request's `lang` and `dir` on `<html>`. The browser-safe helpers (`createTranslator`, `formatMessage`, `localizePath`, `negotiateLocale`, `localeDirection`) are exported from `@absolutejs/absolute/i18n`. See docs/I18N_PLAN.md.
- **Partial prerendering: pre-rendered React and Svelte pages serve a cached shell instantly and stream their `dynamic` slots per request** (`StreamSlot`, `SuspenseSlot`, `StreamingSlot`)
  A pre-rendered page used to be either fully cached or fully rendered per request. Now a streaming slot marked `dynamic` (`<StreamSlot dynamic>` or `<SuspenseSlot dynamic>` in React, the `dynamic` prop or `<!-- absolute:stream dynamic -->` in Svelte) stays a hole in the pre-rendered page. On a route listed in `static.routes`, the build stores the page as a static shell: other slots are resolved into it, and dynamic slots keep their fallback. Each request gets the cached shell at once, before the route handler runs. Only the dynamic slots are then rendered, with the visitor's cookies and headers, and streamed into the page, carrying the request's CSP nonce under `secureHeaders()`. Revalidation (`static.revalidate`) re-captures the shell. Pages without a dynamic slot are pre-rendered as before. Vue and Angular support comes later.
- **Opt-in React Server Components for React pages served from Elysia routes**
  Set `reactServerComponentsDirectory` in absolute.config.ts and put pages in its `pages` folder. Pages are server components: they can be async and read data directly, and that code never ships to the browser. Components marked `"use client"` are server-rendered, then hydrated in the browser. Serve a page from any Elysia route with `handleReactServerPageRequest({ page: asset(manifest, '<Page>RSC'), props })`. `<Suspense>` boundaries stream, and the inline scripts carry the CSP nonce when `secureHeaders()` is on. Install `react-server-dom-webpack` at the same version as `react` (19.2.3 or later). Existing React pages are unchanged. Server Actions, client-side navigation and HMR for these pages are not available yet; edits reload after the dev server restarts.
- **`secureHeaders()`: a strict nonce-based Content-Security-Policy and security headers for every framework** (`secureHeaders`, `getCspNonce`)
  `secureHeaders()` is an opt-in Elysia plugin that sends a Content-Security-Policy with a per-request nonce (`'strict-dynamic'`, no `'unsafe-inline'` for scripts), plus `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `frame-ancestors` and `Permissions-Policy`, each overridable. Every inline `<script>` and `<style>` AbsoluteJS writes carries the nonce: page bootstraps and initial props for every framework, island state, streaming-slot patches, inline page CSS, Svelte and Angular component styles, speculation rules, the error pages and the dev HMR client. The nonce is added where each script is written, so a script injected through `{@html}` / `v-html` / `dangerouslySetInnerHTML` stays blocked. Pre-rendered and ISR pages store the nonce they were rendered with and swap it for each request's, on scripts, styles and `<link rel="modulepreload">`. A page pre-rendered without the plugin is served without a policy and logged. In development the policy also allows the HMR WebSocket and `'unsafe-eval'` (Angular's dev compiler). `getCspNonce()` and the `cspNonce` context value give your own inline scripts the nonce. See docs/SECURITY_HEADERS.md.
- **Self-hosted, preloaded fonts with layout-stable fallbacks from the `fonts` config**
  A new `fonts` option in `absolute.config.ts` downloads Google Fonts (or copies local font files) at build time and serves them from your own origin with content-hashed names and a one-year immutable cache. The build writes one linked stylesheet with `font-display: swap`, a size-adjusted fallback face per family so text does not shift while the font loads, and a `--font-<family>` variable and `.font-<family>` class. Pass `fontAssets(manifest)` to the `fonts` option of `Head` (React, Svelte) or `generateHeadElement`; HTML and HTMX pages get the preload and stylesheet tags automatically. Downloads are cached between builds; a failed download stops the build unless `fallbackToRemote` is set. Hashed static files served by a plain GET now also get the immutable cache header; before, only precompressed copies did.
- **Svelte router: route guards with server redirects, lazy routes, and scroll restoration** (`goto`, `beforeNavigate`, `redirect`, `preloadRoute`, `GotoOptions`, `renderToReadableStream`, `observeViewport`)
  Route guards: a `guard` on `<Route>` or `<Router>`, and `beforeNavigate()` for browser-only checks, runs before `<Link>` clicks, `goto()` and back/forward, and can be async. It returns nothing to allow, `false` to cancel or a URL / `redirect()` to redirect. Cancelling back/forward puts the URL back. Route and Router guards also run during the server render, where a redirect is a 302. Lazy routes: `<Route loader={() => import("./Page.svelte")}>` puts the component in its own chunk, loaded when the route is first visited or when a `<Link>` to it is prefetched, with optional `pending` and `error` snippets. The server renders the real component and the browser loads its chunk before hydrating, so the page doesn't flash. Scroll restoration: while a router is mounted, new navigations start at the top or at the `#hash` target, and back/forward and reload return to where you were. `goto(url, { noScroll: true })` leaves the scroll alone. `goto()` now resolves to what happened (`"committed"`, `"cancelled"`, `"redirected"`, …), and `history.state` holds the router's bookkeeping next to your state, which `page.state` still returns unchanged. Smaller additions that support this: `renderToReadableStream` takes a Svelte `context`, a `settle` callback that can ask for another render pass, and a function for `bootstrapScriptContent`; `observeViewport` and `scheduleHoverPrefetch` take an `onVisible` / `onPrefetch` callback; and the `noScroll` doc on `GotoOptions` now covers `#hash` targets.
- **Vue pages can load data on the server with `useServerData` and hydrate without a second fetch**
  Vue pages could only get server data as props from the route handler. `useServerData(key, fetcher)`, exported from `@absolutejs/absolute/vue`, runs the fetcher while the page renders on the server and writes the result into the page, so hydration shows it without fetching again. A client-side route change, a page that exports `routes`, or `server: false` fetches in the browser instead. It returns `data`, `error`, `pending` and `refresh` refs, with `data` typed from the fetcher. A fetcher that throws on the server renders an error state rather than failing the page (in production the message sent to the browser is generic). Using one key twice in a request fails the page with a clear error outside production. Pages with `client: 'none'` render the data but write nothing into the page, and streaming pages are supported. Streaming-slot patches also no longer land inside the page's own inline scripts.
- **Opt-in Core Web Vitals reporting with `vitals` and `onVital()`** (`onVital`)
  Set `vitals` in absolute.config.ts (`{ endpoint?, sampleRate?, dev? }`) to report LCP, INP, CLS, FCP and TTFB from real visits. A production build bundles a small reporter (web-vitals plus a sender) that every framework's client bundle imports and that static HTML/HTMX pages load with a script tag. Each page load samples once, and a page that reports sends one batch, with its route and navigation type, when it's hidden or closed (`sendBeacon`, falling back to `fetch` keepalive). `prepare()` serves `POST /__absolute/vitals`, validated with a TypeBox schema. It stores nothing; register `onVital(handler)` to forward the metrics to your own store. With `vitals` unset nothing is built or injected, and dev reports only with `dev: true`. It works on pre-rendered pages and under `secureHeaders()`. See docs/WEB_VITALS.md.

Editing a component whose `styleUrl` was a `.less` or `.styl` file showed "Style file not found" for a file that existed, and the update stalled behind the error overlay. The fast path now compiles Less and Stylus with their async compilers. A style that exists but fails to compile reports the compiler's error instead of "not found".   The production server bundle had no source map, so errors logged by `absolute start` pointed into dist/server.js. The Svelte, Vue and Angular SSR page bundles had none either; only dev chained their maps back to the source. The server bundle now gets a linked map, and the SSR page bundles get the same inline-and-chained maps as dev.   The image optimizer created its cache directory (`<build>/.cache/images` unless `images.cacheDirectory` is set) when the server started, so a production server that could not write its build directory crashed on boot with `EACCES` or `EROFS`, even if the app never optimized an image. That is the usual container setup: the build copied in as root and the server running as a non-root user, or a read-only root filesystem. The directory is now created on the first image written to the cache. When it cannot be written, images are still optimized and served, just not cached.   The production server bundle has no source map, but the AbsoluteJS code inside it builds inline source map comments for Svelte and Vue output. Those were template literals starting with `\n`, which Bun's bundler emits as a real newline, leaving a line that starts `//# sourceMappingURL=data:…${…}` in the middle of dist/server.js. Bun read that line as the bundle's own source map whenever it built a stack trace, and warned that it couldn't decode it.

  `handleHTMLPageRequest` and `handleHTMXPageRequest` now render the error convention when a page can't be served (its file is missing or unreadable, or it fails a static-page check). In production every SuspenseSlot patch failed with `renderToStaticMarkup is not a function`, so the fallback stayed on the page. The slot now renders with `renderToReadableStream`, which the bundle keeps.
- **Apps using the Svelte `Head` component build again**
  The packaged Svelte `Head` component imports a small icon helper by relative path, and the package shipped the component without that file, so any app using `Head` from `@absolutejs/absolute/svelte/components/Head.js` failed to build with "Could not resolve ../../utils/iconVersion". The helper now ships next to the components.
- **Svelte HMR keeps component state instead of remounting the page with a number read from the first button**
  On every Svelte component update the HMR client read the first number out of the page's first `<button>`, stored it in sessionStorage and remounted the page with it as an `initialCount` prop. On a page whose first button said "Page 1", editing any component reset a counter elsewhere on the page and injected `initialCount: 1`. The scaffold's demo only worked because its first button happened to be the counter. The client now leaves state to Svelte's own HMR and never reads it from the DOM. The dev server also stopped re-importing the components that import an edited `.svelte` file: `$.hmr` already swaps the edited component in place, and re-importing the page re-created every component under it. - **Svelte pages that use `getContext` / `setContext`, including every Svelte router page, no longer fail under `absolute start`**
  `absolute start` bundled its own copy of Svelte into the production server, while Svelte pages load Svelte from node_modules. The two copies kept separate component context, so a page calling `getContext` or `setContext` (the Svelte router does) answered every request with a 500 `lifecycle_outside_component`. The production server now keeps Svelte external when the app has Svelte pages, so there is one copy.
- **Vue pages with `client: 'none'` set through a same-file const skip their unused client bundle**
  The build drops the client bundle of a Vue page registered with `client: 'none'`, but it only recognised a string literal. `client: CLIENT_MODE` with `const CLIENT_MODE = 'none'` in the same file still built an unused hydration bundle. The scanner now resolves same-file `const` strings for `client` and for the `asset(manifest, …)` key, including `as const`, `satisfies` and the shorthand `{ client }`. A value it can't know at build time (an import, a `let`, a call) keeps the client bundle, which still works and just isn't trimmed.

### Fixed

- **Browser test recordings and reports no longer restart absolute dev**
  Running a visible Playwright test with screenshots, video or tracing caused absolute dev to repeatedly restart the application: test-results, playwright-report, blob-report and .playwright-mcp were treated as source changes. ## 0.20.0-beta.140 — 2026-10-18

### Fixed

- **Dev pages reconnect after a dropped connection without reloading, and keep trying through long outages**
  When the dev-server socket dropped, `absolute dev` pages polled for about 18 seconds and reloaded as soon as the server answered. ## 0.20.0-beta.129 — 2026-10-03

### Added

- **Server code edits in development update the running server in place instead of restarting it** (`onHotDispose`)
  Editing a server module in development used to restart the whole server: a second or more of downtime, every open page dropped, every connection, pool, queue worker and in-memory cache rebuilt. Server modules are now updated in place, statement by statement. A save re-runs only the top-level statements whose own text changed, those that use something that changed, and the importer statements that call a changed export; everything else (database pools, workers, caches, `let` state) is kept as it was. React pages and components the server imports for SSR are updated the same way, so the next request renders the edit. A handler edit typically lands in 1–50ms with nothing else re-run, and exactly one update is applied per save. What a replaced statement started is stopped before its replacement runs: intervals, timeouts and timer chains (cron libraries included), immediates, `process` listeners, extra `Bun.serve` servers (a fixed port is handed over), workers and `onHotDispose` callbacks. Work started by requests and WebSocket events is never stopped. Rebuilding the Elysia app swaps it onto the running server and runs the old app's `cleanup` and the new app's `setup` hooks, as a stop followed by a listen would. An edit that fails to parse or throws while running keeps the previous version serving, and everything it started is rolled back; the fix applies normally. Set `ABSOLUTE_BACKEND_HMR=0` to restart on server edits as before. See docs/BACKEND_HMR.md.

### Fixed

- **Ember and Angular pages and streaming slots render the rebuilt code after an edit**
  In development the Ember and Angular page handlers re-imported a rebuilt page as a `file:` URL with a `?t=` query, and static streaming slot modules were loaded the same way. Bun ignores the query of a `file:` URL and returned the module it had already loaded, so server-rendered HTML kept the old page. `bun --hot` used to hide this by re-evaluating everything. Each now imports a plain path with the query, which Bun does treat as a new module. The mobile build's capture of the server app had the same problem and is fixed too.
- **A React page no longer goes blank when an edit changes both a component and its CSS**
  When a stylesheet changed, the dev client loaded a copy of its `<link>` and removed the original. React 19 hoists a page's `<link>` elements into `<head>` and still owns them, so the next React remount failed with `Failed to execute 'removeChild' on 'Node'` and the page went blank until reloaded. This happened whenever a component edit also changed Tailwind output. The original `<link>` now stays in the document and takes the new stylesheet once the copy has loaded, so nothing flashes unstyled.
- **Editing a module shared by server and pages rebuilds every page that imports it**
  Since 0.20.0-beta.128, editing a module shared by server and frontend code (a formatter, a constants file) could update the server but leave pages of other frameworks importing it on the old code until the next page edit. Frontend dependents of every framework are now rebuilt when a shared module changes.
- **Saving a file next to an unchanged `absolute.config.ts` no longer restarts the dev server**
  Editors and tools that save by writing a temporary file and renaming it make the dev server rescan the folder for recently touched files. A freshly checked-out or copied `absolute.config.ts` counted as changed even when its contents were the same, and the server restarted. It restarted once from the entry watcher and once more from the rebuild watcher. The config is now handled only by the entry watcher, and only when its contents differ from what the server started with.

### Internal

## 0.20.0-beta.123 — 2026-09-28

### Added

- **React Fast Refresh keeps component state: `absolute dev` can run on AbsoluteJS's patched Bun**
  Stock Bun ignores `reactFastRefresh` on `Bun.Transpiler` (oven-sh/bun#32919), so React edits in `absolute dev` remounted the page and lost component state. AbsoluteJS now publishes Bun 1.4.0 with just that fix for every platform Bun ships (github.com/absolutejs/patched-bun). In React projects on stock Bun, `absolute dev` offers it once (Install now / Ask me later / Don't ask again); it installs to ~/.absolutejs/bun, is checked against a pinned SHA-256, and only the dev server uses it, so your `bun` is unchanged. `absolute bun-patch [status|install|remove|reset]` manages it; `ABSOLUTE_PATCHED_BUN=0` opts out.

### Fixed

- **`absolute dev` keeps rebuilding after a syntax error in a React component or an unhandled rejection**
  Under `bun --hot`, Bun counts unhandled rejections that no listener claims and never resets the count; while it is non-zero Bun parks the process in a loop that still serves requests and delivers file-watch events but never runs timers. The server entry imports React pages, so saving a React component with a syntax error made Bun's hot reload reject, and from then on the HMR debounce never fired: every edit was detected and queued, including the one that fixed the error, and nothing rebuilt until the dev server restarted. An unhandled rejection in app code did the same. The dev server now claims unhandled rejections and prints them as before, so its timers keep running.
- **The patched Bun is now a release build, not a canary build**
  `absolute bun-patch install` and the `absolute dev` offer now install `bun-v1.4.0-absolute.2`. The first release was built as a Bun canary build (Bun's build default): it reported `1.4.0-canary.1`, enabled Bun's experimental "bake" server features and made `bun upgrade` track canary. absolute.2 is built with `--canary=off`, as Bun's own releases are; the React Fast Refresh fix is unchanged. Run `absolute bun-patch install` to replace an absolute.1 install.
- **Removed a React HMR CSS branch that only matched the example app**
  The React HMR client had a CSS-only branch that looked up the example app's `ReactExampleCSS` manifest key, so it could never work in another app; the server never sends a CSS-only React update, so it was also unreachable. Removed. Stylesheet edits on React pages go through the general stylesheet swap, now covered by a browser test (the rule applies, component state and the document are kept).
- **React edits that add a component, touch a hook or utility, or create a folder now update the page in place**
  The React fast path told the browser to re-import a single module: the first non-page file in the batch. A new component added to the page re-imported only the new file, so the page never rendered it; a folder created alongside a file became the target and its URL failed to load; and an edited hook or utility whose importer had not been fetched through the module server re-imported just itself, which updates nothing on screen. Every edited file now gets a target (hooks and utilities resolve to the nearest importing component, falling back to the dependents the dependency graph found), directories and deleted paths are skipped, and the client imports them all before refreshing. On stock Bun the remount fallback rendered the changed child in place of the whole page; it now re-imports the page module for the page on screen and ignores edits that do not reach it.
- **React Fast Refresh is used when Bun supports it, instead of always falling back to a remount**
  The dev server decides between React Fast Refresh and the stock-Bun remount fallback by transpiling a probe component. The probe was named `__AbsoluteRefreshProbe`; React Fast Refresh registers only capitalized components, so it reported "unsupported" even on a Bun with the reactFastRefresh fix, and React edits always remounted with a warning. It now uses a capitalized name.
- **A syntax error in a React component shows the error overlay instead of reloading the page**
  A React edit that failed to compile was still broadcast as an update. The browser imported a module that answered 500 and fell back to a full reload, which showed the last good page and no error. The dev server now checks the edited modules compile first and sends the error overlay (file, line and source line) instead; the save that fixes it applies as a normal in-place update. The module server handler and its transform errors also moved to globalThis: after a `bun --hot` reload failed part-way, later imports of the module server got a fresh instance that was never configured, so pre-transforming the changed module silently did nothing.
